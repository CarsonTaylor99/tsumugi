# 07 — User experience

The stated top priority. This document is the spec for it, not decoration.

## Shape: one flow, one mandatory stop

```
  pick game ──► detect ──► unpack ──► extract ──► analyse ──► bible draft
                                                                  │
                                                          ┏━━━━━━━┷━━━━━━━┓
                                                          ┃ BIBLE REVIEW  ┃  ← the only
                                                          ┃  (you, 20min) ┃    mandatory stop
                                                          ┗━━━━━━━┯━━━━━━━┛
                                                                  │
   play ◄── install ◄── build patch ◄── fit ◄── review queue ◄── translate
```

Everything except the bible review has a defensible default and runs unattended. The user's
attention is spent where it compounds — names, pronouns, honorific policy, and ten golden
lines — and nowhere else.

## The run view

What's on screen during the 4–20 hours:

- **Stage, and position within it.** `Translating · 12,480 / 30,112 units`
- **Measured throughput and a real ETA.** Rolling units/minute from the last N chunks, not a
  static estimate. This is what made Fukidashi usable; do the same thing here.
- **A live sample.** The most recent few translated lines, scrolling. It's how you tell in
  ten seconds whether the run is going well, and it's genuinely pleasant to watch.
- **Running quality telemetry.** Validator failure rate, retry rate, judge-score average
  over the 2% sample. A run going wrong should be visible at hour 1, not hour 14.
- **Pause / resume / stop.** Real ones, that checkpoint. Plus the GPU reality of this
  machine: a resumed run after a TDR should cost minutes.

## The bible review screen

Ordered by leverage, not by schema (see `docs/03-bible.md`):
conflicts → names → pronouns → style policy with rendered before/after → golden lines.

The golden-lines step deserves specific attention. Present ~10 representative source lines,
three candidate translations each, let the user pick. Those picks become the few-shot anchors
in every prompt in the run. **This is how the user's taste gets into 30,000 lines**, and it
should feel like the most satisfying two minutes in the tool.

## The workbench

A dense bilingual table. This is the reason the UI is a browser and not XAML.

- **Columns:** scene · speaker · Japanese · English · status · flags · width bar
- **Filters that matter:** by character, by scene, by flag type, by status, by judge score,
  free-text on either language
- **Inline edit.** Editing a line locks it (hard rule 6) and immediately re-runs the
  validators and the width measurement on the new text.
- **In-situ preview.** The line rendered into the calibrated textbox, in the game's font, at
  the game's size, over a real screenshot. Overflow is visible here, not on turn 9,000.
  In a browser this is `canvas.measureText` against the game's own font loaded as a webfont —
  which is exact, not approximate.
- **Context strip.** The surrounding units in reading order, so a line is never judged alone.
- **Systemic fixes.** Where a flag class is systemic (a glossary term, an honorific policy),
  offer the fix at the class level: one decision re-queues every affected non-locked line.
- **Provenance on demand.** Which model, which prompt, when, how many retries. This is the
  answer to "is this weird line the author or the model?" — the same trust mechanism Yohaku
  bakes in.

## Small things that carry disproportionate weight

- **Detect and say so, with evidence.** "KiriKiriZ — `data.xp3` header, TVP strings in the
  exe. Confidence 0.94." Not a silent guess, not a dropdown of 40 engines.
- **Dry-run estimate before committing.** Unit count, duplicate ratio, estimated GPU hours at
  the current bindings. Let the user decide to swap to a smaller `translate` model *before*
  starting, not after hour six.
- **Never silently degrade.** A line that couldn't be translated stays Japanese and is
  marked. A build with unresolved failures says exactly how many.
- **Uninstall works.** The patch installer restores the backup exactly. Knowing you can back
  out is what makes people willing to try it at all.
- **The CLI is real.** Every stage runnable headless with the same semantics. The web UI
  drives the CLI's engine; it is not a separate implementation.

## Deliberately not doing

- Live preview *inside the running game*. Interesting; enormous; not the thesis.
- Multi-user, accounts, cloud sync. Single user, local, one machine.
- A general-purpose CAT tool. This is for VNs. Export to xlsx exists as an escape hatch for
  someone who wants to edit elsewhere, and that's the extent of it.
